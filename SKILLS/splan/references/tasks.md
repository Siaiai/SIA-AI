# 任务、变更与收尾规则

## 任务粒度

一条任务 = **一次会话能改完 + 跑完验证**。超过就拆。

拆分信号：

- 需要改 3 个以上模块或 2 个以上仓库
- 验证耗时 10 分钟以上
- 验收条件写成两段以上"并且"
- 需要等待外部输入（硬件、他人、真机）

拆分方式：按可独立验证的切片拆，例如「协议改完并测试」和「页面接入协议」，不要按文件拆。

## ID 规则

- 阶段前缀 + 序号：`T1-1`、`T1-2`……`T2-1`
- 只增不改；取消的号永久作废，新任务往后排
- 不要在不同文档里重复使用同一个号
- 变更号 `C1`、`C2`……同一文档内连续
- 决策号 `D1`、`D2`……同一文档内连续
- 验收项用 `V-1`、`V-2`……

## 命令参数与定位

- **主对象在前**：需求 / 任务ID / 描述；`--doc <路径>` 可选。旧写法（路径在前）仍兼容。
- **自动定位顺序**（未传 `--doc`）：
  1. `--doc <路径>`
  2. 第一个参数是存在的 `.md`（旧写法）
  3. `AGENTS.md` 里的规划文档指针
  4. `PLAN.md`
  5. `docs/plan.md`
  6. 最近修改的 `*.plan.md`；Obsidian 取最近含 `plan-doc:v1` 标记的笔记
- **多文档命中**：列出候选并询问，不猜。

| 命令 | 新写法（主对象在前） | 旧写法（兼容） |
|---|---|---|
| `/splan-new` | `<标题> [--doc <路径>]` | `<路径> <标题>` |
| `/splan-req` | `<需求> [--doc <路径>]` | `<路径> <需求>` |
| `/splan-next` | `[<任务ID>] [--doc <路径>]` | `<路径>` |
| `/splan-done` | `<任务ID> [--doc <路径>] [--commit / --no-commit]` | `<路径> <任务ID>` |
| `/splan-change` | `<描述> [--doc <路径>]` | `<路径> <描述>` |
| `/splan-check` | `[--doc <路径>]` | `<路径>` |

## 任务优先级

| 级别 | 定义 | 处理 |
|---|---|---|
| P0 | 阻断后续任务或阻塞验收 | 立即做，一次只领一条 |
| P1 | 本轮应做，影响质量 | P0 清空后做 |
| P2 | Backlog，按影响 / 成本排期 | 记录，不阻塞 |
| P3 | 想法 / 远期 | 只记录 |

## 分支策略（D19）

- 执行AI 仅在用户明确要求时，基于当前分支新建 `<type>/<T#-#>-<任务简称>`；未指定则留在当前分支。
- `type` ∈ feature / bugfix / docs / refactor / chore。
- dirty / 非 git：执行AI 先停并报告，不新建分支。
- 规划AI 在当前分支提交；不自动 merge / push：merge 需显式要求，push 禁止。

## 需求关联（为什么有这条任务）

**R = 为什么做**。没有 R 的任务说不清来由。

- 建规划时先登记需求：`R1、R2…`（需求 / 来源 / 状态 / 覆盖任务）
- 每条任务必须挂 `需求：R#`；变更派生的写 `需求：R1（← C2）`
- 变更必须落到某个 R：`新增 R5` / `修改 R1` / `否决 R3`
- 追溯链：**R → T → 提交 / 归档**；C 作用于 R 并派生新 T
- 需求状态：待做 / 待澄清 / 交付 / 变更 / 取消；取消时把覆盖任务一并归档

**需求只有一个入口：需求登记表**。人可以自己改，但：

- 改错别字 / 措辞 / 格式 → 不用通知
- 改"做什么 / 验收 / 范围 / 优先级 / 接口" → 一句话通知规划AI 记 C，同步任务

## 验收写法（验证手段）

任务行写 `验证手段：`，两种写法：

- **命令**：`命令` → 期望结果；由执行AI 跑，回报命令 + 结果
- **人工**：操作步骤 → 判定标准；由用户确认，未确认不勾 `[x]`

```text
验证手段：ctest --test-dir build --output-on-failure → 62/62
验证手段：EIDE 构建 → 0 error，ROM < 128KB
验证手段：人工：打开设置页 → 修改 IP → 重启 → 新 IP 生效且能读参数
```

人工步骤必须可复现：写清操作 + 判定标准。禁止：

- 「确保正确」「功能正常」「体验良好」「看着正常」
- 只写「测试通过」不写命令
- 只有人工主观判断、没有可复现步骤

## 机制复用（防止多机制并行）

**一功能一机制**。同一功能只允许一条机制；并行机制是 bug。

- 任务行的 `机制：` 必填，只能写 `复用 X` 或 `新建 D#`
- 开工前先查 §0 机制登记；有同类机制就扩展它，不要新建
- 新建机制必须先在 §4 决策（D）立记录，写清为什么不能扩展现有
- 执行AI 发现实现会引入新机制：停下，记 D，不要顺手造
- 机制被多任务使用后，登记表“使用者”列同步更新

## 方案单一入口（§3）

- 方案只放规划文档 §3；任务行只保留摘要；不另建方案文档
- 用户可改 §3；规划AI 以 §3 为准，`/splan-next` 先复述方案差异，冲突记 C，不覆盖用户编辑
- 方案讨论：规划AI 给 1–3 个选项，用户确认后落 §3

## 变更操作流（6 步）

```text
1. 先记 C 条目，不判断
2. 定类型：新增 / 修改 / 删除 / 延期 / 否决 / 待定
3. 扫影响五个面：
   [ ] §1 哪些未做要改 / 删
   [ ] §6 哪些已完成要重做
   [ ] §2 契约版本是否要升
   [ ] 测试 / README / AGENTS 是否要同步
   [ ] §0 机制登记是否要同步
4. 定处理：立即做 / 排期 / 延期 / 否决 / 待定
5. 落地：新任务写 ← C#；作废任务进 §6
6. 跑 lint
```

## 三类变化的做法

| 场景 | 做法 |
|---|---|
| 加法（不影响已完成） | 新增 C + 新任务 `T1-19 ← C1`，旧任务不动 |
| 修改（推翻已完成） | 不改旧任务；新开 `T1-20 重做 T1-4（← C1）`；§6 里 T1-4 标"被 T1-20 取代" |
| 删除 / 否决 | §1 任务移到 §6 标"取消 ← C3"，原文保留 |

**最容易做错的是"修改"**：直接编辑旧任务描述会让 AI 以为没做过，导致重做或漏掉回归。

## 状态与归档

- `[ ]` 未做或进行中
- `[x]` 命令验证由执行AI 跑过且通过，或人工验证由用户确认；规划AI 依据回报勾选
- 阻塞写 `（阻塞：原因）→ 解除条件：…`
- 完成 / 取消 / 取代 / 延期全部移出 §1，进归档
- 未确认的需求只进变更表（类型=待定），**不建任务**

## /splan-done 流程（提交归属 D2）

1. **审 diff**：`git status` + `git diff`，只含本任务产出文件；无关改动不提交
2. **核对验证**：核对执行AI 回报的命令验证 + 结果，人工验证等用户确认；不通过 / 未确认不勾 `[x]`；规划AI 不重跑代码验证
3. **更新文档**：§5 一行 + §6 归档 + §0 看板同步 + Splan lint
4. **提交（默认判断）**：本任务文件 + 验证通过 + 文档更新 + lint 0 → 规划AI 提交；有无关改动或失败 → 不提交并说明
5. **开关与 push**：`--commit` 强制提交、`--no-commit` 强制跳过；push 永不自动

- 验证归属：执行AI 跑代码验证并在回报给命令 + 结果；规划AI 只审 diff / 文档 + 跑 Splan lint
- `[x]` 依据执行AI 的验证结果，规划AI 不在自己这边重跑
- 提交归属：规划AI 提交；执行AI 不提交，改动留在工作区
- 默认由规划AI 判断：只提交本任务文件，前提是验证通过、文档已更新、lint 0
- `--commit` 强制提交；`--no-commit` 强制跳过；push 禁止
- 执行AI 只回报 §5 记录，不碰 §5 / §6 / §0，不执行 commit

### 外部笔记回写（R 有 `文档`）

- 任务所属 R 在 §0 需求登记有 `文档` 值时，/splan-done 同步回写该笔记
- 勾选该任务对应的待办项
- 该 R **全部任务完成**后：`状态` 进行 → 完成，写 `完成时间`（带秒）
- 该 R 仍有未完成任务：只把 `状态` 置进行，不写完成时间
- 笔记缺失 / 找不到待办项：不猜，记 WARN，留给人处理

## 会话收尾清单

每次会话结束前必须：

- [ ] §0 状态与实际一致
- [ ] §1 下一条任务明确
- [ ] §5 加一行实施记录（含验证手段与结果）
- [ ] §6 归档完成 / 取消的任务
- [ ] 顶部 `最后更新` 改为今天
- [ ] 跑一次 lint，ERROR 清零

## 执行 AI 硬约束

- 一次只做一条任务；不顺手重构无关代码
- 不 commit / push；提交归属规划AI（D2），执行AI 不提交
- 不覆盖工作区里他人的改动；开工先 `git status`
- 只写当前真实行为；未实现的标「未实现 / 建议」
- 代码片段以仓库真实代码为准，不凭文档臆测
- 结束回复固定写 5 行：改了什么、验证与结果、行为变化、§5 记录、遗留问题；只给事实，下一步由规划AI 定

```markdown
### 4.2 变更记录

- [x] **T1-1 基线** —— 记录分支与构建命令；验证：`ctest` → 20/20；行为：构建/测试命令可复现；结果：通过

| 任务 | 结果 | 关联 | 提交 |

```
